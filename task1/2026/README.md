# Задание №1 — PostgreSQL 18 + клиент на Rust

Одно приложение, два способа собрать подключение.

## Запуск

```sh
make db-up      # postgres на 127.0.0.1:55432
make run        # сборка и запуск
make db-logs    # лог сервера (виден метод аутентификации)
make db-reset   # удалить том и заново выполнить db/initdb/*.sql
make db-down
```

Приложение спрашивает режим (`s` / `i`), затем логин и пароль. Корректные
учётные данные: `usr` / `pass`. Ввод пароля требует настоящего терминала —
он читается напрямую из `/dev/tty`.

## В чём разница

`insecure.rs` склеивает строку подключения libpq:

```
host=127.0.0.1 port=55432 dbname=task1db application_name=task1-app user=<USER> password=<PASS>
```

Драйвер разбирает эту строку обратно, разделяя её по пробелам и `=`, причём при
повторении ключа побеждает **последнее** вхождение. Поэтому всё, что введено
после пробела, становится полноценной опцией подключения.

`secure.rs` присваивает каждое значение отдельному полю `postgres::Config`. Эти
поля попадают прямо в StartupMessage протокола PostgreSQL, где параметры
разделяются нулевыми байтами, — а нулевой байт внутри значения кодировщик
принять отказывается.


### Расширенная таблица полезных нагрузок (Payloads)


| Логин (`user`) | Пароль (`password`) | Поведение в `insecure` | Поведение в `secure` | Влияние на вывод `report()` |
| --- | --- | --- | --- | --- |
| `usr` | `pass` | Подключение к `task1db` | Подключение к `task1db` | Штатное состояние сессии |
| `usr` | `pass dbname=postgres` | Подключение к **`postgres`** | Аутентификация не проходит | `database = postgres` |
| `usr application_name=INJECTED` | `pass` | Имя приложения меняется на **`INJECTED`** | Аутентификация не проходит | `application_name = INJECTED` |
| `usr` | `pass user=postgres` | Попытка подключения от имени суперпользователя `postgres` | Аутентификация не проходит | `user = postgres`<br>`session_user = postgres` |
| `usr` | `pass connect_timeout=1` | Принудительное ограничение тайм-аута до 1 секунды | Аутентификация не проходит | Ошибка таймаута при задержках сети |
| `usr` | `pass options=-csearch_path=information_schema` | Инъекция аргументов командной строки бэкенда | Аутентификация не проходит | `search_path = information_schema, ...` |

---

### Разбор последствий новых полезных нагрузок

> [!NOTE]
> Во всех инъекционных кейсах (`insecure.rs`) драйвер разбирает строку слева направо, и **последнее вхождение каждого ключа перезаписывает предыдущие**. Поскольку пользователь вводит значения в самом конце строки подключения, они переопределяют дефолтные параметры.

#### 1. Подмена пользователя (`user=postgres`)

* **Что происходит:** Строка подключения дополняется параметром `user=postgres`, перекрывая исходный логин `usr`.
* **Последствия:** Приложение пытается аутентифицироваться под административной учётной записью. Если настройки сервера позволяют локальное подключение без строгого пароля (или злоумышленник подобрал/знает хэш), это приводит к критической **эскалации привилегий** в рамках сеанса. Функция `report()` покажет смену текущего пользователя.

#### 2. Манипуляция с таймаутом (`connect_timeout=1`)

* **Что происходит:** Параметр `connect_timeout` принудительно устанавливается в 1 секунду.
* **Последствия:** Создаётся вектор для локального **денежного отказа в обслуживании (DoS)**. Если база данных испытывает высокую нагрузку или сеть слегка задерживает пакеты, приложение мгновенно сбрасывает соединение с ошибкой таймаута, блокируя функционал для легитимных пользователей.

#### 3. Изменение параметров сеанса через `options` (`options=-csearch_path=...`)

* **Что происходит:** Флаг `-c` передаёт переменные конфигурации напрямую бэкенду PostgreSQL в момент старта сессии.
* **Последствия:** Изменение переменной `search_path` перенаправляет приоритет поиска неквалифицированных таблиц в системные схемы (например, `information_schema`). В уязвимых приложениях это открывает возможности для атак типа **Search Path Hijacking**, когда приложение обращается к таблицам, подменяя их содержимое вредоносными объектами.
