# Задание №2 — pinger / heartbeat на Rust

Сервис раз в N секунд выполняет `SELECT version()` и пишет исход: успех — в
stdout, отказ — в stderr, плюс дублирует в файл. Главное требование — **сервис
не должен зависать**: сетевая проблема не отменяет следующую проверку.

«Сеть недоступна» бывает пяти видов, и в трёх из них программа по умолчанию
виснет на минуты или часы — так устроены TCP и ядро. Поэтому запускаются **пять
версий одного образа**, отличающихся только набором защит. Сценарии ниже
показывают один и тот же сбой и кто его переживает.

## Запуск

```sh
make up         # postgres + 5 пингеров + netfault + dozzle
make logs       # логи пяти пингеров в терминале
make status     # что сейчас сломано (правила firewall, пауза, подключения)
make reset      # вернуть всё в исходное
make down
```

Логи всех контейнеров рядом — Dozzle: **http://localhost:58888**.

## Пять экземпляров

Имя сервиса — номер сценария, на котором он зависает.

| Сервис | `connect` | `statement` | keepalive | дедлайн пробы | Переживает |
|--------|:---------:|:-----------:|:---------:|:-------------:|------------|
| `app-fails-1` | — | — | — | — | 0 |
| `app-fails-2` | + | — | — | — | 0, 1 |
| `app-fails-3` | + | + | — | — | 0, 1, 2 |
| `app-fails-4` | + | + | + | — | 0, 1, 2, 3 |
| `app-fails-none` | + | + | + | + | все |

Каждая версия добавляет одну защиту и переживает на один сценарий дальше.
**В сценарии N молчат те, чей номер в имени ≤ N.**

---

## Сценарий 0. Мгновенный отказ

```sh
make fault-reject      # iptables REJECT: ядро отвечает RST
```

Порт «закрыт», ответ приходит сразу. **Все пятеро** пишут
`Connection refused` за миллисекунды и продолжают по расписанию. Это здоровый
отказ — защиты не нужны.

## Сценарий 1. Тишина

```sh
make fault-drop        # iptables DROP: пакеты молча отбрасываются
```

Ответа нет вообще. Ядро повторяет SYN ~127 секунд. `app-fails-1` **молчит**;
остальные отваливаются за 3 секунды (`connect_timeout`) и держат расписание.

Главная причина в жизни — firewall с политикой `DROP` (в отличие от `REJECT`,
он не отвечает, чтобы не выдавать существование хоста).

## Сценарий 2. Сервер занят

```sh
make fault-slow        # APP_QUERY = SELECT version() FROM pg_sleep(30)
```

Соединение есть, сервер работает и не отвечает 30 секунд. `fails1`/`fails2`
ждут все 30; `fails3` и дальше отменяют запрос на 5 секунд — лимит ставит сам
сервер (`statement_timeout`), откатывая работу и освобождая блокировки.

## Сценарий 3. Обрыв пути

```sh
make fault-cut         # долгий запрос, затем DROP на оба направления
```

Соединение установлено, связь пропала (вычищенная запись NAT, упавший маршрут).
Ответ не придёт **никогда**, а TCP этого не замечает — он молчит, пока нечего
передавать. `fails1`…`fails3` висят; восстанавливаются только `fails4` и
`failsnone` — ядро по keepalive само проверяет живость сокета и закрывает его.

## Сценарий 4. Замороженный сервер

```sh
make fault-freeze      # docker pause: процессы стоят, ядро хоста отвечает
```

Самый коварный: сеть исправна, пакеты и keepalive-пробы подтверждаются ядром
хоста, а процесс БД заморожен и не ответит. Все прежние защиты получают честное
«да». Восстанавливается только `failsnone` — у него дедлайн на **всю пробу**:
не «жива ли сеть», а «пришёл ли ответ за N секунд».

```sh
make heal              # снять любую неисправность
```

## Защиты (чем отличаются версии)

```rust
// 1 — свой дедлайн вместо 127 секунд ядра
config.connect_timeout(Duration::from_secs(3));
// 2 — лимит ставит сервер, откатывает запрос
config.options("-c statement_timeout=5000");
// 3 — ядро само проверяет живость сокета (нужны все четыре параметра)
config.keepalives(true).keepalives_idle(..).keepalives_interval(..)
      .keepalives_retries(..).tcp_user_timeout(..);
// 4 — дедлайн на всю пробу: проба в отдельном потоке, цикл ждёт recv_timeout
```

Каждая следующая защита закрывает то, что предыдущая не может; дедлайн на пробу
(4) формально закрывает и 1–3, но спасает только расписание, не чиня причину и
не давая точного диагноза в логе. Сценарии 1 и 3 — одна и та же сетевая
неисправность: разница в том, случилась она до соединения или после.

## Где логи

- **потоки контейнера** — `make logs`, Dozzle (успех → stdout, отказ → stderr);
- **файлы** `logs/fails*.log` — дублирование в файл (п. 1.7), все уровни;
- `make status` — текущие правила firewall, состояние паузы и число
  установленных подключений к базе.

## Проверенные результаты

Прогон PostgreSQL 18.6, интервал 3 с. Жирным — зависания.

| Сценарий | fails1 | fails2 | fails3 | fails4 | failsnone |
|---|---|---|---|---|---|
| 0 `REJECT` | 1 мс | 2 мс | 2 мс | 2 мс | 2 мс |
| 1 `DROP` | **36 с** | 3002 мс | 3007 мс | 3008 мс | 3003 мс |
| 2 `pg_sleep` | **30 с** | **30 с** | 5018 мс | 5015 мс | 5021 мс |
| 3 обрыв | **висит** | **висит** | **висит** | ≈30 с | 10 с |
| 4 `pause` | **висит** | **висит** | **висит** | **висит** | 10 с |

## Устройство

```
app/src/lib.rs         общее: настройки, логирование, одна проба ping()
app/src/bin/fails1..   пять бинарников, отличаются только набором защит
docker-compose.yaml    db, 5 пингеров, netfault (инъекция), dozzle (логи)
Makefile               запуск и неисправности (каждая fault-* сперва heal)
```

Инъекцию вносит `netfault` — он делит сетевое пространство имён с `db`
(`network_mode: "service:db"`), поэтому `iptables` действует на интерфейс
сервера. Правила живут в этом netns и исчезают при перезапуске `db`, так что
сломанную демонстрацию чинит `make reset`.

> TCP-прокси (Toxiproxy и т.п.) для сценария 3 не годится: прокси терминирует
> TCP сам, его ядро отвечает на keepalive — и обрыв пути превращается в
> сценарий 4.
