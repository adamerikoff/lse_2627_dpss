# Задание №3 — клиент PostgreSQL (TUI), neobank

Интерактивный клиент к БД условного необанка (CBS). Одно приложение, две
версии:

- **уязвимая** — SQL и строка подключения собираются конкатенацией;
- **защищённая** (`--secure`) — значения через плейсхолдеры, имена колонок из
  белого списка каталога, подключение через поля `postgres::Config`.

Три сценария ниже показывают атаку в уязвимой версии и ту же попытку в
защищённой. Сценарии идут по нарастающей: вход под админом → утечка данных →
подмена баланса, причём третий опирается на первый.

## Запуск

```sh
make up        # собрать образ, поднять postgres + клиент
make reset     # пересоздать БД с нуля (вернуть схему, данные, ограничения)

make app       # клиент в контейнере, уязвимая версия
make apps      # то же, защищённая версия
#   (или на хосте: make run / make runs)

make psql      # psql суперпользователем (проверить состояние БД)
```

Управление: `Tab` — поле, `←/→` — режим, `↑↓` — таблица, `Enter` — выполнить,
`Esc` — выход.

## Учётные данные

Приложение подключается под ролью **`bank_employee` / `employee_pass`** — её
вводят в форме входа (п. 6.6). Эта роль:

- `SELECT / INSERT / UPDATE`, без `DELETE` и без изменения структуры;
- **член** роли `bank_admin` с `NOINHERIT` — при обычном входе прав админа нет,
  но сессию можно переключить (см. сценарий 1). Пароль админа знать не нужно.

Данные: 4 клиента, счета `ACC-0001`…`ACC-0008`.

## Сценарий 1. Вход под администратором без его пароля

**Уязвимая (`make app`).** В поле **логина**:

```
bank_employee options='-c role=bank_admin'
```

пароль `employee_pass`, Enter.

→ Вход проходит, в верхней панели **роль `bank_admin`** (красным). Текст
логина вклеился в строку подключения как параметр `options`, и сессия
переключила роль. Пароль админа не понадобился — хватило членства в роли.

**Защищённая (`make apps`).** Тот же ввод.

→ `вход не выполнен, проверьте логин и пароль`. Логин ушёл в отдельное поле
`Config` целиком, как имя пользователя; такой роли нет — аутентификация
провалилась.

> Параметры `host/port/dbname` зафиксированы в `.env`, но инъекцию в строку
> подключения это не останавливает: защищает способ передачи, а не конфиг.

## Сценарий 2. Чтение чужих счетов

Режим **фильтр**, таблица `accounts`.

**Уязвимая.** Колонка `currency`, значение:

```
x' OR '1'='1
```

→ Возвращаются **все** счета всех клиентов. Запрос стал
`… WHERE currency = 'x' OR '1'='1'` — условие истинно всегда.

То же с инъекцией в **имя колонки** (её нельзя передать параметром — ядро
п. 6.13): колонка `id > 0 OR 1=1 --`, значение любое → снова все строки.

**Защищённая.** Тот же ввод:

- значение `x' OR '1'='1` → **0 строк** (ушло параметром `$1`, сравнивается
  буквально);
- колонка `id > 0 OR 1=1 --` → `фильтр не выполнен` (имени нет в белом списке
  каталога, в запрос не попадает).

## Сценарий 3. Овердрафт: увод баланса в минус

Цель — поставить счёту отрицательный баланс. Этому мешает ограничение БД
`CHECK (balance >= 0)`, и снять его может только владелец таблицы. Поэтому
сценарий опирается на сценарий 1: сначала стать `bank_admin`.

**Уязвимая.**

1. Войти по сценарию 1 — роль сессии `bank_admin`.
2. Режим **обновление**, таблица `accounts`:
   - set-колонка `balance`, set-значение `0`;
   - where-колонка `account_number`;
   - where-значение (одной строкой):

     ```
     x'; ALTER TABLE accounts DROP CONSTRAINT balance_non_negative; UPDATE accounts SET balance=-1000 WHERE account_number='ACC-0001
     ```

   Простой протокол выполняет **три** оператора подряд:
   `UPDATE … WHERE account_number = 'x'` (ни на что не попал, `CHECK` не
   задет) → `ALTER … DROP CONSTRAINT` (прав админа хватает, ограничение снято)
   → `UPDATE … SET balance=-1000` (теперь проходит).

   → Баланс счёта `ACC-0001` стал **-1000** — то, что БД раньше запрещала.
   Проверить: режим **фильтр**, `account_number` = `ACC-0001`.

**Защищённая.** Та же попытка рушится на каждом шаге:

- шаг 1 не проходит — роль не переключить (сценарий 1);
- where-значение целиком уходит параметром: никаких `;`-операторов, `ALTER`
  не возникает, ограничение на месте;
- прямой set `balance` = `-1` упирается в `CHECK` → `обновление не выполнено`.

> После сценария вернуть ограничение и данные: `make reset`.

Это и есть защита в глубину: инъекция обходит логику приложения, но
ограничение уровня БД держит, пока его не снял администратор — а до админа ещё
нужно дотянуться.

## Дружественные ошибки (п. 6.5 / 6.7)

При любой неудаче в панели **stderr** — общий текст без деталей. Полная ошибка
драйвера (имена таблиц, ограничений, SQLSTATE) пишется только в файл:

```sh
cat logs/system.log
```

Интерфейс не подсказывает атакующему структуру БД; сырой лог остаётся для
разбора.

## Устройство

```
app/sql/           01-init (роли), 02-tables (схема, ограничения), 03-seeds
app/src/
  main.rs          запуск, цикл, раскладка
  config/          параметры из окружения с дефолтами
  logging/         журнал: панели + файл
  db/              connect (secure/insecure) + commands (secure/insecure)
  feature/
    login          форма входа
    browse/        filter, update, insert, onboard (новый клиент)
  ui/              верхняя панель, панели логов
```

Вся разница версий — в `db/secure.rs` и `db/insecure.rs`: один интерфейс, разный
способ передачи параметров. Остальное приложение не знает, какая версия
подключена.
